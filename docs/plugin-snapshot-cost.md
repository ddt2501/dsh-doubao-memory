# per-turn 住相 · 成本核算（2026-11-10）

> 结论先行：**钱不是问题**。住相每轮多的一次调用约占一轮总成本的 **2.5%**；
> 真正贵的是**住相进 history 之后的常驻上下文**（一个月后每轮多付的 cache-read 是生成成本的 **5.6 倍**，且随会话线性增长）。
> 真正疼的不是钱，是**每轮 +1.5s 首 token 延迟**。
>
> 核算脚本：`RUNTIME/scripts/cost-snapshot.py`（可重跑，数据全部来自本机 session log）

---

## 1. 单次调用的 token 预算

按 `snapshot-sop.md` §2.1 的 5 输入 + 提示模板：

| 输入 | 区间 (tok) |
|---|---|
| `current_message` | 0 – 200 |
| `last_snapshot` | 50 – 150 |
| `rolling_summary` | 350 – 500 |
| `soul_active_dims` | 10 – 50 |
| `relevant_themes` | 30 – 100 |
| 提示模板 + 硬/软约束 + 动机提示 | 200 – 400 |
| **输入合计** | **640 – 1,400**（中位 ~1,020） |
| **输出**（硬约束上限） | **≤ 150** |

**每次调用：~1,020 in + ~150 out，全新 token，零缓存命中**（提示词太短，缓存写不划算）。

## 2. 主对话每轮的真实用量（实测，2026-11-10）

来源：session log 的 `assistant/message` usage 聚合，取本会话 **53 个"轻轮"的中位数**（≤3 次模型调用 = 用户正常聊天的形态）：

| 项 | 中位数 |
|---|---|
| 每轮模型调用 | **1 次** |
| fresh input | 2,797 tok |
| **cache read** | **604,329 tok** |
| output | 609 tok |

> ⚠️ 这个会话的上下文已经涨到 ~60 万 token，所以 cache_read 极大。**一轮的成本是被上下文长度主导的，不是被这一轮的输入主导。**
> （均值会被少数超长轮拉偏：fresh_in 均值 167,808、cache_read 均值 620,794——所以一律看中位数。）

## 4. 住相的"常驻成本"——**这条在 2026-11-10 之后消失了**

> ⚠️ **原分析的前提是"住相以 user 角色进 history"**。用户拍板"住相是 agent 的自我意识的投射"后，
> 通道改成了 **system prompt 的 section** ⇒ **住相不进 history** ⇒ 下面这个"一个月后每轮比生成还贵 5.6 倍"的问题**不存在了**。

原问题（已作废，仅留档）：

住相以 user 角色进 history 时，每轮给会话**永久**增加 ~150 tok，之后**每一轮**都要为这段常驻上下文付 cache-read。
按 20 轮/天算，一个月后常驻 **+90,000 tok**：

| 档位 | 之后每轮多付 cache-read | 是生成成本的多少倍 |
|---|---|---|
| Flash 级 | $0.00090 | 5.6× |
| MiniMax M1/M2 | $0.00270 | **5.6×** |
| Sonnet 级 | $0.02700 | 5.1× |

**当时的结论**：住相跑一个月之后，"养着它"比"生成它"还贵 5 倍多，而且这笔钱每轮都在付。

**现在的成本形态**：

| 项 | 变化 |
|---|---|
| history 常驻 | **0**（住相不进 history） |
| system prompt | 每 step +~150 tok（前缀缓存命中 ⇒ 增量成本≈cache-read 价，约为输入价的 0.1 倍） |
| 长会话风险 | **消失**——system prompt 每个 step 重新组装，compaction 不影响它，也不随轮数累积 |

> 也就是说：**原来最大的那个成本项，被语义澄清顺手解掉了。**
> 语义决定（"它是自我意识"）和成本决定（"别让它进 history"）**指向同一个方案**——这也是为什么值得先把语义说清楚。

## 5. 延迟：现在**不是**用户的等待时间

- 住相生成本身要 **2.3–2.6s**（实测，见下）
- 但**它不再阻塞用户的等待**——生成在后台跑，触发点是 **agent 转 idle**（本轮话说完之后）
- 用户体感延迟 = **0**

> ⚠️ **2026-11-10 实测修正**：生成耗时是 **2.3–2.6s**，不是 SOP 估的 1.5s。
> OpenClaw 时期的 metrics 也证实——`RUNTIME/manas-system/data/snapshots/metrics/2026-09~10/*.jsonl`
> 里 30+ 条记录的 `generation_time_ms` 中位数约 **2.8s**（区间 1.4s – 22s）。
> 固定开销约 2.3s：输出 58 token 是 2.4s、输出 131 token 是 2.6s ⇒ **token 数不是瓶颈，固定开销才是**。

### ⚠️ 并发坑：别跟主对话抢同一个 provider

最早把生成挂在 `pre-step step 1`——那时主对话的模型调用还在飞，
两条请求打同一个 API key ⇒ 实测 **20.2s** 且**返回空响应**（连兜底都是空的）。

⇒ 触发点改成 **agent 转 idle**：那时 provider 是空的，生成回到 2.4s。

### 现在的延迟账

| 谁 | 等多久 |
|---|---|
| 用户发完话 → 助手开始回 | **0**（住相不在这一轮里） |
| 助手回完 → 后台生成住相 | 2.4s（不影响任何人） |
| 下一轮助手看到住相 | 滞后一轮 |

### 如果哪天要改回"同轮准确"

代价是每轮 **+2.4s** 的首 token 延迟（用户能感觉到"她想了一下"），
收益是住相说的是"这一刻的我"而不是"上一刻的我"。
零延迟变体（现在这个）的代价是**滞后一轮**。这个取舍用户已经拍过一次（"同意 1"）。

## 6. 结论

| 问题 | 答案 |
|---|---|
| 每轮多一次调用贵吗？ | 不贵。占一轮总成本 **2.5%**；即使按 Sonnet 价，30 轮/天也只有 ¥34/月 |
| 那什么贵？ | ~~住相进 history 的常驻上下文~~ → **已解决**：改走 system prompt 的 section，不进 history |
| 延迟还疼吗？ | 不疼了。生成在后台（agent 转 idle 时），**用户体感延迟 = 0** |
| 语义清楚了吗？ | 清楚了：「住相是 agent 的自我意识的投射」→ 走 **system prompt 的 section**（指令区，和 SOUL 同处），不是 user 角色消息 |
| 已定的 | 每轮 1 次调用 · section 通道 · 后台生成（滞后一轮）· 超时 30s · A/B 降级 · 第二人称算软约束 |
| 已拍板（2026-11-10） | ① 第二人称**不升级**为硬约束，保持 `strictSecondPerson: false`；② **接受滞后一轮** |

---

## 7. 两项待决的最终决定（2026-11-10）

**① 第二人称是否升级为硬约束 → 不升级。**

- 理由：中文里"你"含义太宽（可能指用户、可能指自己），硬约束会**误杀**——
  住相被判不合格 → 重试 → 预算花完 → 走兜底文案 ⇒ **质量反而下降**。
- 住相已经用三重手段守住语义归属：`system prompt` 的 section（不是 user 消息）
  + 框架句明说"是我自己的视角，不是用户的话" + 生成 prompt 里本就写着"不要第二人称"。
  第二人称偶尔出现**不改变归属**。
- 要升级随时一行配置：`snapshot.strictSecondPerson: true`（代码里已经实现，
  `lib/snapshot/instrumental.js` 的 `validate()` 会把它当 hard 失败并重试）。

**② 住相滞后一轮 → 接受。**

- 代价：住相说的是"上一刻的我"，不是"这一刻的我"。
- 收益：**用户体感延迟 = 0**（生成在 agent 转 idle 后台跑）、每轮 1 次调用、成本不变。
- 语义上仍成立：住相是"我的自我意识的投射"，上一刻的我也是我。
- 用户此前已拍过"同意 1"（生成挪后台）。**此项无待决。**
